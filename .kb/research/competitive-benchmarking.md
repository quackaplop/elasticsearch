# Competitive Benchmarking Infrastructure

**Repo:** `elastic/competitive-benchmarking` (private)
**Explored:** 2026-03-31

## What Is It

Elastic's Kubernetes-based competitive benchmarking framework. Runs identical workloads across multiple data stores (Elasticsearch, ClickHouse, OpenSearch, Victoria Metrics, Mimir, Prometheus, Loki, Qdrant, Victoria Logs) on identical hardware to produce objective performance comparisons.

The logs benchmarking portion is based on a fork of [ClickBench](https://github.com/ClickHouse/ClickBench) adapted for Elasticsearch. The metrics benchmarking is original.

## Two Benchmark Domains

### Metrics
- Synthetic host metrics (CPU, memory, filesystem, network) generated by `metricsgenreceiver`
- Products: Elasticsearch, Victoria Metrics, Mimir, Prometheus
- Queries: PromQL + ES|QL (time-series aggregations, rate calculations, top-K, group-by)
- Primary scenario: 270 minutes of data at 1-second intervals, scale 100 hosts → 225M events

### Logs
- Two datasets:
  - **ClickBench hits**: 100M records from public GCS bucket (`gs://cb-logs-dataset/clickbench/`). Available in **Parquet**, JSON, CSV (all zst-compressed).
  - **Kubernetes multiapp logs**: 169M records, JSONL format, OpenTelemetry schema.
- Products: Elasticsearch, ClickHouse, OpenSearch, Loki, Victoria Logs
- Queries: ~50 SQL queries (ClickBench standard) + ES|QL translations
- Query types: aggregations, filters, string matching, analytics, sorting, COUNT/SUM/AVG/DISTINCT

## How It Runs

1. **GitHub Actions** trigger (daily 6 AM UTC or manual)
2. **matrix-generator** (Go) expands YAML config into parallel jobs
3. **oblt-cli** creates EKS cluster with Helm-deployed databases (separate node pools per product)
4. **BenchBuilder** (Go) orchestrates: download datasets → create indices → ingest data → measure storage → run queries → collect results
5. Results published to monitoring Elasticsearch cluster with Kibana dashboards

### Key Tools
- **BenchBuilder**: Main orchestrator. Reads scenario YAML, runs hooks (download, ingest, query), collects metrics
- **Vegeta**: HTTP load testing tool for query workload (rate-limited, timed)
- **httploader**: Bulk ingestion component for logs
- **metricsgenreceiver**: Synthetic metrics generator for OTEL pipeline

## Datasets and Storage

All datasets stored in **public GCP Cloud Storage buckets** — no authentication required. Downloaded dynamically before benchmark via `HttpDownload` hooks with local caching.

| Dataset | Records | Format | Source |
|---------|---------|--------|--------|
| ClickBench hits | 100M | Parquet, JSON, CSV (zst) | `gs://cb-logs-dataset/clickbench/` |
| K8s multiapp logs | 169M | JSONL (zst) | `gs://cb-logs-dataset/` |
| Synthetic metrics | 225M | Generated in-memory | metricsgenreceiver |

**Critical for our use case:** The ClickBench dataset is already available in **Parquet format** in the GCS bucket. ClickHouse can query Parquet natively. This is the natural starting point for external data source benchmarking.

## External Data Source Relevance

### What Exists Today
- All benchmarks **pre-load data** into each database before querying. No database reads from external files during the benchmark.
- ClickBench dataset exists as Parquet in GCS — but it's converted to JSONL and bulk-ingested into ES, not queried as external Parquet.
- ClickHouse in these benchmarks also pre-loads data (SQL INSERT), not querying external files.

### What We'd Need to Add for External Data Source Benchmarking
1. **New scenario type**: Query Parquet/JSON files directly from blob store (S3/GCS) without pre-loading
2. **ES|QL external source queries**: `FROM "s3://bucket/hits.parquet" | WHERE ...`
3. **ClickHouse external source queries**: `SELECT ... FROM s3('s3://bucket/hits.parquet', 'Parquet') WHERE ...`
4. **Apples-to-apples comparison**: Same Parquet files, same queries, same hardware, same blob store
5. **Metrics to capture**: Query latency (cold + warm), throughput, memory usage, data transfer

### ClickHouse External Data Capabilities (what we'd compare against)
ClickHouse has mature external data support:
- `s3()` / `gcs()` table functions for direct Parquet/JSON/CSV reads from blob stores
- `url()` table function for HTTP sources
- Native Parquet reader with column pruning, predicate pushdown, parallel reads
- Can create external tables backed by S3 Parquet files

### Gap Assessment
- The benchmarking infrastructure (BenchBuilder, Vegeta, EKS clusters, result collection) is all reusable
- Need new scenario YAMLs that skip the ingestion phase and go straight to querying external files
- Need to upload the ClickBench dataset to S3 (it's in GCS today — or use GCS directly)
- Need ES|QL queries translated for external source syntax
- Need ClickHouse queries translated for `s3()` table function syntax

## Deployment Details

### Hardware
- Default: `c8gd.4xlarge` (AWS Graviton3, 16 vCPU, 32 GB RAM)
- Intel variant: `c7i.4xlarge`
- Cluster sizes: 1-node (12GB/12core) to 3-node (12GB/12core each)
- Storage: EBS gp3 (default 250 MiB/s, 3000 IOPS) or local SSD

### Benchmark Parameters
- Warmup: 15s-1min per query
- Query rate: 3 req/s (rate-limited) or backpressure
- Workers: 1-8
- Duration: 3-5 minutes per query set
- Timeout: 5 minutes per query
- Cache invalidation between queries

## Configuration

### Scenario YAML Structure
```yaml
suite:
  name: "logs-clickbench"
  hooks:
    pre_start:
      - id: download-dataset
        type: HttpDownload
        parameters:
          source: "https://storage.googleapis.com/cb-logs-dataset/clickbench/datasets/hits.json.zst"
          destination: "clickbench"
          auto_extract: true
    pre_run:
      - id: create-index
        type: Elasticsearch
        parameters:
          method: PUT
          path: "/hits"
          body_file: "mapping.json"
  benchmarks:
    - id: ingest
      type: httploader
      ...
    - id: query
      type: vegeta
      ...
```

## BenchBuilder Architecture (from elastic/benchbuilder repo)

**Repo:** `elastic/benchbuilder` — cloned at `/Users/oleglvovitch/github/mine/arrow/benchbuilder`

### How it works
- BenchBuilder is a Go application, packaged as a Docker image, deployed via Helm chart to K8s
- It orchestrates: download data → create indices → ingest → measure storage → run queries → collect results
- Results published to centralized monitoring ES cluster (GCP)

### Benchmark types (exhaustive list)
`httploader`, `clickhouse-cli`, `metricsgenreceiver`, `otelcollector`, `logsgenreceiver`, `filebeat`, `elastic-agent`, `auditbeat`, `metricbeat`, `vbench`

**There is no `noop` type.** Every suite requires at least one benchmark (ingestion step). Queries (`QueryGenerator`, `Vegeta`) are `post_run` hooks attached to a benchmark.

### Hook types
- `HttpDownload` — downloads files from HTTP/GCS URLs to BenchBuilder's local filesystem
- `StaticInput` — declares expected record count for metrics
- `QueryGenerator` — generates and runs queries against the database (post_run hook)
- `Vegeta` — HTTP load testing for query workload (post_run hook)
- `RefreshIndex`, `CleanUpDestinationIndex`, `IndexStats`, `component_template` — ES-specific lifecycle hooks

### HttpDownload destination
Files download to `{artifactsPath}/{destination}/`. The `artifactsPath` is BenchBuilder's working directory inside its pod. **Not shared with database pods** — this is critical for external data source work.

### Local development
```bash
# Start ES + ClickHouse + OpenSearch locally
make up-clickbench

# Run ClickBench scenario
go run main.go run -b examples/clickbench/clickbench.yaml

# Stop
make down-clickbench
```

Docker Compose configs in `deploy/` directory. BenchBuilder connects to other stacks via Docker networks.

### Smoke test datasets (for local dev)
- `hits-500k.json.zst` — 500K records (JSON, for ES httploader)
- `hits_0-smoke.parquet.zst` — small Parquet (for ClickHouse)
- Full dataset: `hits.parquet.zst` — 100M records, ~14GB

### Production deployment flow
1. GitHub Actions trigger (cron daily 6 AM UTC or manual "create cluster and run benchmark")
2. `matrix-generator` expands `cron-benchmark-configs.yaml` into parallel jobs
3. `oblt-cli` creates EKS cluster (AWS, `c6gd.8xlarge` Graviton3, 32 vCPU, 64 GB RAM, local NVMe SSD)
4. Helm charts deploy: ES (via ECK), ClickHouse, BenchBuilder, monitoring agents
5. BenchBuilder executes scenario, publishes results to monitoring ES cluster
6. Cluster auto-destroyed after expiry (configurable, default +8h)

### Running on-demand
GitHub Actions → "create cluster and run benchmark" workflow. Select branch, deployment template, scenario file. No PR needed — runs from any branch.

### Key constraint for external data sources
`HttpDownload` saves to BenchBuilder's pod. For `file://` queries, the file must be on the **database pod's filesystem**, not BenchBuilder's. Solutions:
1. **Shared hostPath volume** in K8s deployment (mount same path to BB + ES + CH pods)
2. **S3/GCS URLs** — both engines read remotely. No shared volume needed. Same latency for both = fair comparison.
3. **Docker Compose** (local dev) — shared filesystem by default, no issue.

### Existing ClickBench queries
43 matched ES|QL + SQL query pairs already exist in `clickbench.yaml`. For external data source variant, replace `FROM hits` with external path/URL in each query.

## Next Steps for External Data Source Benchmarking

1. **Phase 1 — Local dev**: Use BenchBuilder's Docker Compose (`make up-clickbench`), dummy `httploader` ingestion, queries in `post_run` with local file paths. Validate queries work.

3. **Phase 3 — Deployment template**: Add shared hostPath volume for local-disk variant (optional, for pure reader performance without S3 latency).
4. **Phase 4 — Production run**: Add to `cron-benchmark-configs.yaml` for daily CI runs alongside existing benchmarks.
5. **Phase 5 — JSON comparison**: Same approach with JSON/JSONL files.
5. **Phase 5 — JSON comparison**: Same approach with JSON/JSONL files (ClickHouse `s3()` with JSONEachRow format vs ES|QL external JSON)
